# Increment 4: AI Provider Port & Local Adapter Agent

## Status: ✅ COMPLETE (2026-07-26)

All phases implemented, tested, and verified. Ready for Increment 5.

See: [increment-4-completion.md](docs/roadmap/increment-4-completion.md) for full implementation summary.
Implement Helix's optional, user-governed AI provider system with Ollama local-first defaults, comprehensive fallback robustness, and explicit adoption control. Preserve the modular boundary and ensure AI unavailability never breaks core workflows.

## Scope & Constraints

### What This Agent Owns
- AI provider port contract and adapter factory pattern
- Ollama local adapter with health checks and graceful degradation
- No-op fallback adapter for deterministic workflows
- AI provider lifecycle (init, availability detection, error recovery)
- Optional AI orchestration layer with explicit user activation
- Comprehensive test strategy (unit, integration, contract, chaos)
- AI-specific documentation (governance, provider setup, fallback behavior)

### What This Agent Avoids
- Modifying core domain models to require AI (AI must be optional)
- Logging reflections, prompts, or sensitive user content by default
- Implementing auth/identity (deferred behind port)
- Semantic retrieval or graph visualization (later increments)
- Production deployment or cloud provider integrations (Increment 10)
- Clinical or diagnostic language in AI interactions

### Architectural Rules (from ADRs)
- **ADR-006**: AI is optional; adapters implement `AIProviderPort`; fallback is deterministic
- **ADR-007**: Ollama is local-first; no cloud provider required for MVP
- **ADR-008**: User controls memory lifecycle; AI-derived facts must be reviewed and accepted
- **ADR-001**: Changes respect modular monolith boundaries; cross-module access through REST

## Implementation Strategy

### Phase 1: Port & Factory Pattern
- Define `AIProviderPort` interface (prompt, response contract, error handling)
- Implement `AIProviderFactory` for adapter instantiation and health checks
- Create `NoOpAIAdapter` for deterministic fallback (returns fixed suggestion structure)
- Create `OllamaLocalAdapter` with connection retry, model availability detection

### Phase 2: Orchestration Layer
- Add `AIOrchestrationService` in `applications/` to manage provider lifecycle
- Implement provider health check with exponential backoff
- Add configuration for local Ollama endpoint, model name, timeout defaults
- Ensure AI unavailability emits log and gracefully degrades to deterministic path

### Phase 3: Integration Points
- Integrate AI orchestration into existing suggestion flow (optional enhancement)
- Keep deterministic suggestion generation as primary path
- Add optional AI-assisted retrospective insights (without replacing user capture)
- Ensure all AI outputs are labeled as "AI-assisted" with confidence metadata

### Phase 4: Testing Strategy
- **Unit tests**: Adapter initialization, error handling, retry logic
- **Integration tests**: Port contract compliance, factory behavior
- **Contract tests**: AIProviderPort interface conformance
- **Chaos tests**: Simulate Ollama timeout, connection failure, model not found
- **End-to-end**: Fallback behavior verification when AI unavailable

### Phase 5: Documentation
- Update ADR notes with implementation decisions (e.g., health check interval, timeout values)
- Document Ollama setup steps for local development
- Document fallback behavior guarantees in failure-and-fallback-behavior.md
- Update architecture diagrams (ai-and-memory-view.md, runtime-view.md)
- Add troubleshooting guide for provider setup issues
